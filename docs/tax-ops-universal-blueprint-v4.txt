The Challenge

Tax Operations processes hundreds of work items per week arriving through six different channels — email, Slack, voicemail, agency portals, VP direct assignments, and automated system alerts — with no unified system to capture, route, or track them.

The result: invisible work, missed SLAs, duplicated effort, reactive escalations, and no real-time operational visibility for leadership. Kitty cannot confirm a ticket was created. Robin cannot see the true health of all five pillars simultaneously. This document defines the architecture to fix that.

The Solution: Universal Blueprint & Jira Workflow Architecture

A standardized, automated workflow system that makes all Tax Ops work visible, routed, and tracked — regardless of how or where it arrives.

Six Core Capabilities

Zero Dark Work — Every item entering Tax Ops from any channel becomes a standardized Jira ticket within minutes

Auto-Routing — Work type, client segment, and jurisdiction automatically assign the right team and DRI — no manual triage

SLA Enforcement — Priority-based SLA clocks start automatically; aging alerts fire before deadlines are breached

Leadership Visibility — Robin and Kitty have a real-time command center: queue health, aging items, P1 escalations, and workload distribution

Cross-Ticket Tracing — Refiled work links back to original rejections; escalations trace to root cause; audit trails survive RCA reviews

Automation-Ready — 18 native Jira automation rules defined; extends existing routing agent; AI expansion roadmapped for Phase 3

How Every Work Item Flows

Work Arrives (Email · Slack · Voicemail · Agency Notice · VP Assignment · System Alert)

→ Auto-Classify (Routing agent sets Work Type, Pillar, Priority, Client Segment)

→ Ticket Created (Standard fields set, SLA clock starts, DRI assigned)

→ DRI Notified (Slack alert with ticket link and SLA deadline)

→ Worked & Closed (SLA tracked · Leadership visible throughout)

Builds on existing infrastructure: The current routing agent (email + voicemail) is the foundation. Phase 2 extends it to set Jira fields automatically. New intake channels (Slack, agency notices, VP quick-create) layer on top with minimal additional build.

Section 01: Universal Ticket Hierarchy

A consistent hierarchy is the foundation of all visibility, SLA tracking, and routing. Every piece of work must live at the correct level — Epic overuse buries reporting; Task overuse hides structure. Use these definitions universally across all pillars.

Epic

A regulatory season, program, or sustained operational initiative. Spans weeks or months. Has a defined start/end or recurring cadence. Contains multiple related work packages. Used for leadership rollup and headcount justification.

When to create: Recurring tax season · Multi-state program · Process improvement initiative · Agency audit engagement

Tax Ops examples: Q3 2026 Filings Season · 2025 W-2/W-2C Processing · Puerto Rico Tax Reform Implementation · Annual SUI Rate Refresh · NWPEO Notice Resolution Program

Story

A discrete deliverable or outcome within an Epic. A complete unit of work with a clear done state. Owned by one DRI. Typically completable within 1–5 business days. Crosses a single employer, state, or work type boundary.

When to create: Single employer filing · One agency notice response · One amendment request · Client escalation resolution

Tax Ops examples: File Puerto Rico W-2Cs for Employer X · Respond to Ohio BWC Audit Notice #2024-001 · Process rejected SUI check for Client Y · Refile Q2 OH Withholding for Employer Z

Task

An individual action required to complete a Story. A single-person, single-day (or shorter) unit of work. Has clear input and output. Can be validated. Represents one distinct action in the workflow sequence.

When to create: Pull and validate employer data · Upload file to agency portal · Confirm receipt/confirmation number · Draft client communication

Tax Ops examples: Pull W-2C data from source system · Validate Ohio withholding calculation · Submit filing to agency portal · Log confirmation number

Subtask

A granular step within a Task — used for collaboration or phased work. Use sparingly. Only needed when a Task has distinct sub-phases or requires a second person (e.g., a QA reviewer). Do not create subtasks for single-person sequential steps — those are just comments/work log entries.

When to create: QA reviewer validation step · Second approver sign-off · Parallel work on the same Task by two ICs

Tax Ops examples: IC Self-QA: Validate calculation · Manager QA: Approve submission · Upload confirmation copy to drive

Hierarchy Decision Guide

Question to ask
	If YES → Level
	If NO → consider

 

Does this span multiple work packages across weeks?
	Epic
	Probably a Story or below

Is this a complete deliverable for one employer/client/state?
	Story
	Probably a Task inside an existing Story

Is this a single action with a clear input/output (sub 1 day)?
	Task
	Could be a Subtask or a work log comment

Does this need a second person (QA/approver) or run in parallel?
	Subtask
	Just a sequential step — use work log / checklist

Hierarchy Rule: Ad hoc requests from Slack, email, voicemail, or leadership that are standalone work items (no parent Epic yet) should be created as Stories first, then linked to the appropriate Epic once one exists. Never leave an orphaned Task with no parent Story — this is the primary cause of invisible work.

Section 03B: Cross-Project Relationship Standards ✦new

Why this matters: Without a shared relationship taxonomy, cross-ticket reporting is impossible. RCA chains break. Repeat issue analysis fails. Penalty attribution has no audit trail. This section defines the complete set of valid issue link types — every ticket relationship must use one of these, and no others.

Universal Issue Link Taxonomy

Relationship (Jira Link Type)
	Meaning
	When to Use

 

refile of
	This ticket is a new submission for work that was previously rejected or failed
	When creating a refile after a rejection; link new ticket to the original rejected ticket

corrects
	This ticket fixes an error made in the linked ticket
	Amendments, 941-X, W-2C corrections; link to the filing that contained the original error

caused by
	The problem described in this ticket was caused by the linked ticket
	Root-cause attribution; helps identify systemic failure patterns

blocks
	This ticket cannot be progressed until the linked ticket is resolved
	Dependency modeling; upstream dependency that must complete first

escalates
	This ticket represents an escalation of the issue tracked in the linked ticket
	When a DRI-level issue is escalated to a Manager, Director, or VP level ticket

related notice
	This ticket and the linked ticket both involve the same agency notice or filing event
	Multi-ticket agency notice response; group all related work

payment for
	This ticket represents the ACH/payment action for the linked filing ticket
	Separate the filing action from the payment action while maintaining traceability

spawned from
	This ticket was created as a result of work done in the linked ticket (unexpected scope discovery)
	New work discovered mid-execution; keeps the parent scope clean

duplicate of
	This ticket is a duplicate of the linked ticket
	Triage; close the duplicate, do not delete — it preserves the audit trail

supersedes
	This ticket replaces the linked ticket as the current work item
	Version replacement; old ticket linked for history, new ticket is the active DRI assignment

Mandatory Linking Rules

Every refile ticket must carry a refile of link to the original at creation

Every amendment/correction ticket must carry a corrects link to the originating filing

Every escalation ticket must carry an escalates link to the triggering ticket

Payment tickets for filed returns must carry a payment for link to the filing ticket

No ticket may be closed as duplicate without a duplicate of link — deleting duplicates breaks audit chains

Relationship Governance

Jira automation will flag any ticket closed without a required relationship link (refile, correction, escalation) and notify the Pillar Manager to remediate within one business day.

Three-Deadline Framework ✦new

Every ticket can carry up to three distinct deadline fields. They are independent of each other and must not be conflated.

1. Regulatory Deadline (Field: Regulatory Deadline)

What it is: The statutory deadline set by the agency, tax authority, or law. This is the hard legal due date.

Who sets it: Routing agent (from email/notice metadata) or DRI manually at ticket creation

Behavior: Immovable. Changing this field requires manager approval and a comment explaining the change. If work is not completed by this date, penalty risk is automatic.

Examples: IRS Form 941 quarterly due date · State SUI quarterly filing deadline · W-2C submission deadline per IRS Publication 15-A

2. Operational Deadline (Field: Operational Deadline)

What it is: An internal cutoff imposed by operational constraints — ACH processing windows, physical mailing schedules, batch submission cutoffs, or client communication windows.

Who sets it: DRI or Pillar Manager at ticket creation or during planning

Behavior: Earlier than or equal to Regulatory Deadline. The team must complete the work by this date to hit the Regulatory Deadline safely.

Examples: ACH must initiate by 2pm for same-day settlement · W-2C batch must be submitted to processing by Friday noon for Monday mailing · State portal submission batch closes at 11:59pm on the 14th

3. SLA Deadline / Due Date (Field: Due Date)

What it is: The internal team target calculated automatically from Priority and Client Segment (the SLA Bucket). This is the team's self-imposed service level.

Who sets it: Auto-calculated by Jira automation from Priority × Client Segment at ticket creation

Behavior: May be earlier or later than the Operational Deadline. SLA breach warnings fire based on this date. Does not replace Regulatory or Operational Deadlines.

Deadline Priority Order (in case of conflict): Regulatory Deadline ≥ Operational Deadline ≥ SLA Due Date. If Operational Deadline < SLA Due Date, Jira automation fires an alert: "Operational constraint is tighter than SLA — adjust priority or DRI assignment."

Operational Readiness Framework ✦new

Operational Readiness is a field independent of Jira workflow status. It answers a different question: not where is this ticket in the process, but are the preconditions for the next action actually met?

A ticket can be In Progress (workflow status) but Not Ready to File (operational readiness). These are different states and must not be conflated.

Operational Readiness Values

Value
	Meaning
	Typical Workflow Status

 

Not Ready
	Default state; preconditions unknown or unmet
	To Do / Backlog

TPA Pending
	Waiting for third-party administrator action before work can proceed
	In Progress / Blocked

Client Action Complete
	Client has provided all required documentation or authorization
	In Progress

Ready to File
	All data validated, portal access confirmed, regulatory deadline confirmed, DRI ready to submit
	In Progress

Ready for Refile
	Original rejection documented, correction validated, new submission ready
	In Progress

Compliance Approved
	Legal/compliance team has signed off on the work
	In Progress / Pending Review

Engineering Validated
	Engineering team has confirmed technical fix is deployed and data is correct
	In Progress

Ready for Payment
	Filing confirmed; ACH initiation authorized; window confirmed
	In Progress

Readiness vs. Status Matrix

Workflow Status
	Valid Operational Readiness Values

 

Backlog / To Do
	Not Ready only

In Progress
	Not Ready / TPA Pending / Client Action Complete / Ready to File / Ready for Refile / Engineering Validated / Ready for Payment

Blocked
	Not Ready / TPA Pending / Client Action Complete

Pending Review
	Compliance Approved / Ready to File / Ready for Refile

Done
	Compliance Approved / Ready for Payment / Ready to File (completed)

Why This Matters

Without the Operational Readiness field:

A DRI can set a ticket to "In Progress" and leave it there indefinitely without communicating that work is actually gated on a client response or TPA action

Robin has no way to distinguish "In Progress and on track" from "In Progress but actually waiting for something external"

SLA clocks run against tickets that cannot be acted upon

With the Operational Readiness field:

Robin can filter for all tickets that are In Progress but Not Ready or TPA Pending — and take action on the blockers

Kitty can see that her assigned work is "Ready to File" vs. "Waiting on client"

Automation can trigger different alerts based on Readiness value (e.g., Client Action Pending for > 48 hours → client success team notified)
